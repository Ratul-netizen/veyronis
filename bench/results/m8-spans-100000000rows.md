# M8 — the two measurements, at 100M spans

`docs/M8-observability.md` closed §2.2 and §2.6 with an obligation rather than a claim:
the trace lookup's bloom filter and the service map's join were both *bets*, and the
document said in as many words that assuming was not enough. This is the run.

- rows: `100000000` spans, `20000000` traces of 5 spans each
- tenants: 3 · hosts: 5 000 · services: 40
- range: `2026-08-21 00:00:00.014` .. `2026-08-27 23:59:59.995`
- ClickHouse `26.8.9.10`, 4 cores, in a VM on the development machine
- harness: `bench/scripts/load.sh spans 100000000` then `bench/scripts/m8.sh`

**Both bets were right, and one of them had a parameter nobody had chosen.**

---

## §2.2 — finding one trace

The sort key is `(tenant_id, resource_id, observed_at)`. A trace's five spans are on five
different hosts, so nothing in that key narrows the search; the bloom filter on `trace_id`
is the entire mechanism. The question was how much it actually prunes.

| index                     |    rows read | granules |  cold ms |
|---------------------------|-------------:|---------:|---------:|
| none                      | 33 447 936   |    4 083 | 1 882 – 2 015 |
| `bloom_filter` (default)  |    827 392 – 868 352 | ~101 – 106 |  108 – 148 |
| `bloom_filter(0.001)`     |     73 728 – 90 112  |    9 – 11 |   49 – 141 |

Each row is one cold lookup that found its five spans. **371× fewer rows than a scan**,
and the index is what stands between a 2-second lookup and a 50-millisecond one.

### The parameter nobody had chosen

`bloom_filter` with no argument takes ClickHouse's default false-positive rate of
**0.025**. One granule in forty survives the filter by accident, which at this scale is
about a hundred granules of false positives around the five that hold the trace.

At `0.001` that becomes nine to eleven granules — near the five the data actually
occupies. The index grows from 94 MiB to 177 MiB, which is **one per cent** of an 8.26 GiB
table for an order of magnitude on the query the table exists to answer.

`0008_spans.sql` took the default because nobody looked at what it was. Fixed in
`ch-migrations/0009_spans_trace_index.sql`.

### Wall clock here is noisy; rows read is the number to trust

On four cores in a VM the per-query overhead is tens of milliseconds and the cold read is
dominated by it — the same configuration measured 49 ms once and 141 ms another time
while reading the same handful of granules. Rows read does not move like that, and it is
the property of the index rather than of the host.

## §2.6 — the service map

A self-join on `parent_span_id` over one hour, filtered to one tenant, excluding
same-service edges and the nil service — the statement
`uops_query::servicemap::compile_service_map` emits, run against the benchmark table.

| window | spans in it | edges | rows read | cold ms |
|---|---:|---:|---:|---:|
| 1 hour | 198 415 | 120 | 3 211 264 | 472 – 583 |

**Usable for a screen**, which is the bar §2.6 set. Two things worth knowing:

- **It reads 16× more rows than the window holds.** The time filter is not leading in the
  sort key, so the window costs whole granules of every host that was active in it. That
  is the same trade the sort key was chosen for in M0 and it is working as designed —
  contiguity for one resource, at the price of scanning for one hour.
- **The edge count is capped at 500 and this found 120**, which is the whole map for 40
  services. A real estate with a long tail of rare calls would hit the cap, and the API
  reports `truncated` for exactly that reason.

No fallback is needed. The view keyed on `parent_span_id` that §2.6 named as the escape
hatch stays unbuilt, and the reason it stays unbuilt is now a number rather than optimism.

## Storage

```
   ┌─table─┬─compressed─┬─uncompressed─┬─ratio─┬─skip_index─┬─granules─┬──────rows─┐
1. │ spans │ 8.26 GiB   │ 20.50 GiB    │  2.48 │ 177.11 MiB │    12268 │ 100000000 │
   └───────┴────────────┴──────────────┴───────┴────────────┴──────────┴───────────┘
```

A 2.48 ratio against `logs`' 6.12 at the same row count. Spans compress worse and should:
a log row is mostly one long body of repetitive English, while a span is seventeen short
columns of high-entropy ids. 85 bytes per span on disk.

At this shape, `spans`' 7-day retention is **~8 GiB per 100M spans per week**.

## The trap, recorded because it produced a confident wrong answer first

The first version of `m8.sh` ran each query five times and took the median, which is what
a benchmark normally does. Every configuration then reported **40 960 rows in 9 ms** —
indexed, unindexed, and with the index explicitly ignored.

ClickHouse remembers which granules matched a predicate. The second run of a lookup reads
only the granules the first one found, so the median of five was a measurement of that
memory. `use_skip_indexes = 0` does not help: the pruning has already happened.

It was believable. 40 960 rows is five granules, which is exactly what a perfect index
would read, and it would have been written up as a triumph.

The fix is that **every trace id is used exactly once**, which makes each number a single
cold observation rather than a median. That is a real loss of precision and the honest
trade: a median of warm runs is precise about the wrong thing.

A second, smaller version of the same mistake: `X-ClickHouse-Summary` is sent as a header
before the query finishes unless progress headers are configured, so reading it reports
whatever had been counted at flush time. It gave a plausible 40 960 for a full scan.
The statistics in a `FORMAT JSON` body are written after the query completes.
